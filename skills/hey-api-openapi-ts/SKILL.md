# Developing with @hey-api/openapi-ts

`@hey-api/openapi-ts` generates production-grade TypeScript from an OpenAPI spec: types, a high-level SDK, an HTTP client, runtime validators, state-management hooks, server stubs, and mocks. The generated output is driven by a **config file** that lists an `input`, an `output`, and an array of **plugins**. Almost everything is a plugin — even the default types and SDK.

The job is usually one of: (1) set up codegen from scratch, (2) add or reconfigure a plugin, (3) write application code that consumes the generated output, or (4) debug a generation or runtime issue. Figure out which, then act. Don't hand-write the config from memory of an older tool (this is not `openapi-typescript` or `openapi-generator` — the API differs); follow the patterns below.

## The core mental model

There are three layers, and the user can stop at any of them:

1. **Types** (`@hey-api/typescript`) — TS interfaces for every schema, request, and response. Zero runtime cost. Always generated by default.
2. **SDK** (`@hey-api/sdk`) — an ergonomic typed function (or class method) per operation, sitting on top of the client. Handles auth, serialization, optional validation/transformation. Generated by default.
3. **HTTP client** (e.g. `@hey-api/client-fetch`) — the thin layer that actually sends the request. Fetch is the default; Axios/Next.js/Nuxt/Angular/Ky/ofetch are alternatives.

On top of those, optional plugins generate **validators** (Zod, Valibot, …), **state-management** hooks (TanStack Query, SWR, Pinia Colada, …), **server** code (Fastify, Nest, Hono, …), and **mocks** (MSW, Faker, …). The output folder is a build artifact — tell the user never to hand-edit files in it, because the next generation run overwrites them.

## Setup workflow (codegen from scratch)

Do this when there's a spec but no `openapi-ts.config.ts` yet.

1. **Confirm the environment.** Requires Node.js 22+. The package is in initial development, so pin an exact version: `npm install @hey-api/openapi-ts -D -E` (or pnpm/yarn/bun equivalent). Install exactly because minor bumps can be breaking.
2. **Locate the input.** It can be a local path (`./openapi.json`), a URL (`https://.../openapi.json`), or a Hey API registry slug (`'my-org/my-api'`). Use whatever the user gives you. If they only have a running server, the spec URL is usually `/openapi.json`, `/swagger.json`, or `/api-docs`.
3. **Pick the plugins** based on the user's stack (see "Choosing plugins" below). Default to Fetch + types + SDK if they don't specify; that's the minimum useful client.
4. **Write `openapi-ts.config.ts`** in the project root using `defineConfig` (see template in `references/config.md`).
5. **Add an npm script** so regeneration is one command:
   ```json
   { "scripts": { "openapi-ts": "openapi-ts" } }
   ```
   Then `npm run openapi-ts`. For a one-off, `npx @hey-api/openapi-ts -i <input> -o <output>` works without a config.
6. **Verify** the output folder appears (typically `client.gen.ts`, `types.gen.ts`, `sdk.gen.ts`, plus any plugin files) and that it type-checks.
7. **Configure the client instance** — almost always `baseUrl`, often auth. See `references/clients.md` for `setConfig` vs `runtimeConfigPath` vs `createClient`.

Then show the user a short usage example calling one real operation from their spec, not a generic `getPet`.

## Choosing plugins

Match the user's stack rather than dumping every plugin in. A few quick reads:

- **Plain TS / Node / scripts** → Fetch client + SDK + types. Done.
- **React app** → add `@tanstack/react-query` plugin for hooks, or SWR. Keep the Fetch client unless they use Axios already.
- **Next.js** → use the `@hey-api/client-next` client (handles `next: { revalidate }` etc.).
- **Vue / Nuxt** → `@hey-api/client-nuxt` and optionally Pinia Colada or TanStack Query (vue).
- **Angular** → the Angular client + Angular plugin.
- **Need runtime validation** → add a validator (Zod is the common default; Valibot is lighter). Wire it through the SDK's `validator` option so requests/responses are checked. See `references/validators.md`.
- **Building the server too** → Fastify / Nest / Hono / Express / oRPC plugins generate route handlers or contracts from the same spec.
- **Testing / Storybook** → MSW plugin for request mocking, Faker/Chance/Falso for fake data.

When the user names a framework, read the matching section of the relevant reference file rather than guessing option names — plugin option names are specific (e.g. `operations.strategy`, `validator`, `transformer`) and easy to get subtly wrong.

## Consuming the generated output

This is where most day-to-day work happens. Patterns:

- **Call an operation:** `import { getPetById } from './client/sdk.gen'; const { data, error } = await getPetById({ path: { petId: 1 } });`. The SDK returns `{ data, error, request, response }` — there's no throw by default, so check `error`.
- **Pass params:** options object with `path`, `query`, `body`, and `headers` keys, all typed from the spec.
- **Per-call client override:** pass `client` or `baseUrl` in the options to hit a different instance/host for one call.
- **TanStack Query:** the plugin exports `xQueryOptions()` / `xMutation()` / query-key helpers; spread them into `useQuery`/`useMutation`. See `references/state-management.md`.

When writing app code, prefer importing from the SDK (`sdk.gen.ts`) over the raw client — it carries the types and auth wiring.

## Reference files

Read the one that matches the task. Each expands on option names, edge cases, and full examples that are too detailed for here.

- `references/config.md` — the config file shape: `input` forms, `output` options, multiple jobs / job matrix / merging specs, the parser, the Vite plugin, programmatic `createClient()`, CLI flags.
- `references/clients.md` — every HTTP client (Fetch, Axios, Next.js, Nuxt, Angular, Ky, ofetch), and the three ways to configure an instance (`setConfig`, `runtimeConfigPath` + `createClientConfig`, `createClient`), interceptors, auth, custom instances.
- `references/sdk-and-types.md` — the SDK plugin in depth: flat (tree-shakeable functions) vs instance (classes), `containerName`, `nesting`, built-in `auth`, `validator`, `transformer`, generated code examples; plus the TypeScript and JSON-schema plugins.
- `references/validators.md` — Zod (v4 default, v3 available), Valibot, and the others; how validation hooks into the SDK for requests vs responses; transformers.
- `references/state-management.md` — TanStack Query, SWR, Pinia Colada, Zustand: what gets generated (query options, infinite queries, mutations, query keys) and how to use it.
- `references/ecosystem.md` — server frameworks (Fastify, Nest, Hono, Express, oRPC, Angular, Koa, Elysia, Adonis, TanStack Start), mocks (MSW, Faker, Chance, Falso, Nock, Supertest), custom plugins/clients, and the migration/integrations notes.

For anything not covered, the live docs index is at `https://heyapi.dev/llms.txt` and individual pages live under `https://heyapi.dev/docs/openapi/typescript/...`. The full option list is the `UserConfig` interface in the openapi-ts source on GitHub.

## Things that bite people

- **Pin the version.** `-E` / exact installs. The library publishes breaking changes in minors during initial development.
- **Don't edit generated files.** Configure via the config file, `setConfig`, or a `runtimeConfigPath` file — never by hand-patching `*.gen.ts`.
- **Errors aren't thrown.** SDK calls resolve to `{ data, error }`. Check `error` rather than wrapping in try/catch expecting a throw (unless you've added a throwing interceptor).
- **Validation has a runtime cost**, so it's off by default. Turn it on deliberately via the SDK `validator` option, and consider validating responses only if request shapes are already trusted.
- **Self-signed HTTPS specs** in dev need `NODE_TLS_REJECT_UNAUTHORIZED=0` in the environment for the generator to fetch them.
- **Plugin name strings are exact**: `@hey-api/client-fetch`, `@hey-api/sdk`, `@hey-api/typescript`, `@tanstack/react-query`, `zod`, `valibot`, etc. A typo silently skips the plugin.
